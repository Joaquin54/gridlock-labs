# Load gap report: `context-files/*_load.csv` → `backend/src/db/schema.ts`

Audit of the two load files against the Drizzle schema, in both directions, plus the eleven decisions
that closed the gaps. Written 2026-09-26, resolved 2026-09-27.

The CSVs are read-only inputs generated by `build_load_csvs.py` in the data repo. Nothing in this report
asks for a change to them: **every count and value domain in the load spec matched the files exactly.**
All gaps were on the schema side.

## 3. The specific checks

**1. `verified` confidence.** The DB layer never lost it: `CONFIDENCES` still contains `verified`, the
view still ranks it, `verified_by` exists, and `verification_note` is a note-like column. So `verified`
loads as-is for 103 projects and 234 points, with **no mapping** (Decision 10). What was dropped is only
at the API layer — `clampConfidence` in `backend/src/lib/confidence.ts` collapses `verified → high`, and
no route returns `verified_by` / `verified_at` / `verification_note`. That is a route task, listed in §5.

**2. `source_url` vs `osm_url`.** The proposed `osm_url = coalesce(source_url, osm_url)` is **not**
lossless. `source_url` is set on 326 rows, `osm_url` on 122, **both on 12**, and of those **7 hold
different strings** — every one the same OSM object in two notations (`osm:way/318318141` against the
full `https://www.openstreetmap.org/way/318318141`). Under the coalesce those 7 would lose the full URL;
coalescing the other way would lose `source_url` on 314 rows. Decision 5 added the column instead, so
nothing is lost. (Worth noting for the data side, not a load problem: one of the 5 identical pairs,
`DESC:6810 J` seq 2 "Santee City", stores a map-search URL rather than an object URL.)

**3. Nullable point confidence.** The column was `NOT NULL DEFAULT 'low'`, so all 119 NULLs would have
been silently filled with `low` — a defaulted value. Decision 3 made it nullable with no default.
Interaction worth recording: `project_points_confidence_floor_ck` (`lat IS NOT NULL OR confidence =
'low'`) evaluates to NULL, and so passes, for the 9 unlocated points that now carry NULL confidence. The
constraint is left as it is.

**4. Enums and CHECKs.** Compared against the distinct CSV values: `utility`, `owner`, `project_type`,
`work_type`, `start_date_source`, `status`, and both `confidence` columns all matched. Only
`POINT_METHODS` was short, by `hifld` and `eia860` — 238 of 445 rows (Decision 4). `voltage_kv` satisfies
`> 0`; `cost_usd` fits `numeric(14,2)`.

**5. Types.** `projects.id` and `project_key` are `text`; `in_service_raw` is `text`; `lat`/`lon` are
`double precision`, not a scaled numeric; `project_points.project_id` is `text`. All correct as they
stood — no change needed.

**6. The centre rule in `project_geo`.** The view takes the midpoint of the first and last **located**
points ordered by `seq`, `avg()` for `multi_station`, and NULL when nothing is located. Against this data
that is exactly the guide's rule: the 9 unlocated points each sit on a 2-point line whose sibling is
located, so the view returns that single located point; and **no 3-point line has a located middle with an
unlocated end**, the case where "first located" and "seq 1" could diverge. Recomputing all 252 centres
from the CSV independently reproduced the view's rule, including the four pinned spot values to 6 dp.
No change to the view's centre expressions.

**7. Distance.** `backend/src/queries/overlaps.ts:105-110` uses haversine on a sphere with
**R = 3958.8 mi**, rounds to 2 decimals and filters `distance_mi < maxMiles` on the rounded value.
Recomputed independently from the CSVs: 77 pairs in scope and 77 across all owners, closest
`GPC:16007`–`DESC:6810 O` at 2.33 mi / 578 d, farthest `GPC:19523`–`DESC:06367 A - C, H` at 24.93 mi /
250 d, sum 1252.70. Correct as it stands.

**8. CSV columns with nowhere to go.** `confidence`, `is_border`, `evidence`, `source_url` and `note` all
had no target; all five were given columns (Decisions 1, 5, 6, 7, 8). `in_service_raw`, `status` and
`cost_usd` already had columns. `match_score` and `match_name` already had columns.

**9. Schema columns nothing fills.** `line_miles`, `miles_source`, `cost_low`, `cost_high` and
`verified_at` take NULL — they are the BONUS/savings and verification-timestamp fields, and no CSV column
carries them, so the export CSVs and the savings section stay blank. `source_page` was the one NOT NULL
column without a default and is now nullable. `project_geo` is entirely derived.

## 4. Decision 9 — the derived floor after hardening

`coalesce(pt.confidence, 'low')` now wraps both the `location_confidence` rank and `confirmed`, so an
unreviewed point drags a project down instead of being skipped.

| | stored `projects.confidence` | `location_confidence` before | after |
|---|---|---|---|
| verified | 103 | 140 | **103** |
| high | 5 | 0 | 0 |
| medium | 13 | 6 | 4 |
| low | 131 | 106 | 145 |

Disagreements with the stored rollup fall from **53 to 14**, all of one shape — stored `medium` → derived
`low` (9 rows) and stored `high` → derived `low` (5 rows), each a project carrying an unreviewed
NULL-confidence point: `DESC:6846 A`, `GPC:10143`, `GPC:11821`, `GPC:17993`, `GPC:18668`, `GPC:19601`,
`GPC:19632`, `GPC:19950`, `GPC:20002`, `GPC:20010`, `GPC:20428`, `GPC:20784`, `GPC:20793`, `GPC:20874`.
Not driven to zero, by instruction. Honest note: `confirmed` counts 103 both before and after, so that
half of the change is defensive rather than a fix to an observed error.

## 6. Applying schema changes to Tiger

**Don't run `drizzle-kit push` against Tiger as-is: it sees Timescale's `pg_*` views and prompts to
rename/drop them.** Apply schema changes via `drizzle-kit export` + a reviewed transaction, or add a
`tablesFilter` in `drizzle.config.ts` first and verify it hides those views.

What happens concretely: the Tiger database carries `timescaledb`, `timescaledb_toolkit`,
`pg_stat_statements` and `pg_buffercache`, and the last two put four views in `public` —
`pg_buffercache`, `pg_buffercache_numa`, `pg_stat_statements`, `pg_stat_statements_info`. `schema.ts`
declares one view, so drizzle-kit's diff sees one view to create and four it does not know about, and
enters `viewsResolver → promptNamedWithSchemasConflict` to ask a human whether `project_geo` is a rename
of one of them. It needs a TTY, and a wrong answer renames or drops a monitoring view owned by an
extension. `pushSchema` from `drizzle-kit/api` exits 1 silently on the same database.

The route taken instead, which touched nothing outside the three relations:

```
cd backend
bunx drizzle-kit export --sql > /somewhere/outside/the/repo/gridlock_schema.sql
```

`export` diffs `schema.ts` against an empty state, so it never reads the database and writes no migration
files. Review the output — it must contain only `CREATE TABLE projects` / `project_points` with their
constraints and indexes, the `project_geo` view, and the one `ALTER TABLE project_points` that adds its
own foreign key; no `DROP`, no `ALTER` on anything else, no `pg_*` reference — then apply it inside a
single `BEGIN … COMMIT` that aborts on the first error, and confirm afterwards that the four `pg_*` views
are still there.

## 7. Verified against Tiger, 2026-09-27

PostgreSQL 18.6 on Timescale, database `tsdb`. The three relations were created by the reviewed
transaction above; the four `pg_*` views were counted before and after and were unchanged. The loader then
ran with `--target=tiger` and committed, and all 29 parity checks pass against Tiger — the same 29 that
pass on PGlite, including 252/445 row counts, the 9 NULL coordinate pairs, the 119 NULL point
confidences, `verified` 103, every `in_service_date` and lat/lon equal to the CSV, all 252 centres within
5 ft of the rule recomputed from `points_load.csv`, 77 pairs in and out of scope, the closest and farthest
pairs, 1252.70 mi summed, and 16 low-confidence pairs. `/health`, `/projects`, `/projects/:id`,
`/overlaps` and `/stats` all return 200, and `/overlaps?inScope=true&maxMiles=25` returns 77.

Two corrections to earlier notes, both checked on the live database:

- **`code_review_2026-09-26.md` finding 1 does not fire in the app's path.** The raw postgres.js client
  does return `date` as a JS `Date`, as the review says. But every app query goes through drizzle's
  postgres-js session, and `db.execute` returns `date` as a `'YYYY-MM-DD'` string there — verified both
  directly and on the wire, where `/projects/:id` emits `"in_service_date": "2025-12-31"`. The finding is
  correct about the driver and wrong about the consequence. It stays open only for any code that talks to
  postgres.js without drizzle.
- **`/stats` reports the wrong confidence split.** It returns `{total: 77, high: 49, medium: 0, low: 28}`.
  The total is right; the buckets are not, because `pair_confidence` still derives from
  `project_geo.location_confidence` (with `verified` clamped to `high`) rather than the new
  `projects.confidence`. The DB-level check reads 16 low pairs, the API says 28. First item for the route
  pass in §5.

## 8. `--replace`, and the point-confidence reversal (2026-09-27)

The data side regenerated `points_load.csv`: point `confidence` no longer has NULLs (the 119 became `low`,
the team's floor rule) and `match_name` is filled on 357 of 445. Verified before reloading, by diffing both
files against the rows already in Tiger: `projects_load.csv` identical on all 18 comparable columns across
252 rows; `points_load.csv` differing **only** in `confidence` (119 rows) and `match_name` (247 rows), with
0 key and 0 coordinate changes.

`project_points.confidence` is therefore `NOT NULL` again, with **no default** — a missing level fails the
load instead of being silently filled, which was the original objection to `DEFAULT 'low'`. Two things were
deliberately left alone so a fresh database stays identical to Tiger:

- `project_points_confidence_ck` keeps its `IS NULL OR …` branch. It is now unreachable, but rewriting it
  would mean dropping and recreating a constraint on Tiger that no decision covered.
- The view keeps `coalesce(pt.confidence, 'low')`. Also now redundant for real rows, but still load-bearing
  for the `left join`'s NULL when a project has no points at all.

The column was flipped by a reviewed `ALTER` applied **inside the reload transaction, after the insert** —
never `drizzle-kit push` (§6). It lives in `POST_INSERT_DDL` in `backend/scripts/load-tiger.ts`:

```sql
ALTER TABLE project_points ALTER COLUMN confidence SET NOT NULL
```

`SET NOT NULL` rescans the table, so a single NULL confidence aborts the whole reload — the constraint
verifies the data rather than trusting it.

`--replace` is now implemented. In one transaction it deletes `project_points` then `projects` (children
first; the cascade is not relied on), inserts both files, applies `POST_INSERT_DDL`, runs every check, and
commits only if all pass. Rehearsed on PGlite as a genuine reload — first load 34/34, `--replace` over the
populated tables 34/34 — and its rollback was proved by corrupting one coordinate: 32/34, transaction
aborted, all 252/445 rows still present with the original coordinate intact.

**Tiger reload, 2026-09-27: 34/34 checks passed, committed in 1.4 s.** The four new checks are point
confidence `verified 234 / high 2 / medium 8 / low 201`, NULL confidence `0`, and `match_name` non-null
`357`. Every other value is identical to the previous run — project confidence 103/5/13/131, 77 pairs in
and out of scope, closest 2.33 mi, farthest 24.93 mi, 1252.70 summed, 16 low-confidence pairs, all
coordinates and all 252 centres unchanged, `location_confidence` still `{verified 103, medium 4, low 145}`
disagreeing with `projects.confidence` on the same 14 projects. Confirmed afterwards:
`project_points.confidence` is `is_nullable=NO` with no default, the four `pg_*` views are still there, and
`/health`, `/projects`, `/projects/:id`, `/overlaps` and `/stats` all return 200 with `/overlaps` at 77.

## 9. The shared `points` table, and the deliverable views (2026-09-27)

Two additive changes went in after §8, each by a reviewed transaction. Every statement
applied to Tiger is kept in `backend/db/applied/`, in order, with a README — that
directory is the record of what is actually in the database. `schema.ts` stays the
source of truth; nothing reads `applied/` at runtime.

### `points` + `project_points` as the join

436 located join rows sit at only **273 distinct coordinates**, and **104** of those are
shared by two or more projects. `points` now holds one row per physical location and
`project_points` gained a nullable `point_id` (FK, `ON DELETE RESTRICT`, indexed), NULL
on exactly the 9 unlocated rows. The `point_usage` view reports who shares each point.
Grouping is by exact coordinate, never by name — four names occur at two different
places each — and that is safe because the closest two distinct coordinates are 137.3 m
apart. `docs/points_join_report.md` has the full analysis, including four projects whose
two line ends resolve to the same coordinate (reported, not fixed) and the finding that
**no point is shared across utilities**, so the shared-asset bonus cannot be argued from
coordinate identity.

Coordinates are now stored in two places, deliberately: `project_points.lat/lon` (what
every existing query reads) and `points.lat/lon`. Nothing was switched over — see the
routes-affected table in §5.

### `overlap_table` and `project_table`

Two views shaped like the organizers' "Project | Overlap Table" template, sitting
alongside `project_geo` and changing nothing about it or the overlap queries.
`scripts/export-deliverables.ts` renders them through `src/lib/deliverable.ts`, and the
output is **byte-identical** to the golden copies in `context-files/deliverable/`
(`overlaps.csv` 14,945 bytes / 77 pairs; `projects.csv` 49,430 bytes / 252 projects),
verified with `cmp` on both PGlite and Tiger. `GET /export/overlap-table.csv` and
`GET /export/project-table.csv` serve the same bytes through the same formatter, so the
download and the checked-in files cannot drift.

Number formats come from the golden files, which are the spec, not from prose: point
`lat`/`lon` are **exactly 6 decimals** (`32.352120`, `33.321000`), centres are up to 7
decimals with trailing zeros stripped (`-81.1487715`), `distance_mi` is exactly 2, and
`in_service_date` is `M/D/YYYY` unpadded **in this view only** — the table keeps ISO.
`overlap_id` is numbered by the *unrounded* distance, and the export orders by that id
rather than by `distance_mi`, so a rounded tie can never emit rows out of id order.

### Regenerating the deliverable

```
cd backend
bun scripts/export-deliverables.ts --target=tiger --out ../docs/deliverable
```

`--target=pglite` does the same from a throwaway database built from the CSVs, which is
how the byte comparison is checked without touching Tiger.

## 10. Reloading after the data repo regenerates the CSVs

```
cd backend
bun scripts/load-tiger.ts --dry-run               # revalidate both files, write nothing
bun scripts/load-tiger.ts --target=tiger --replace
```

The delete order is `project_points`, `projects`, `points`; the insert order is
`projects`, `points`, `project_points`. Confirmed on Tiger with the `point_id` CHECK
already in place: 44/44 checks, committed. The two views need no attention on a reload —
they are derived, so a corrected point flows into the deliverable with no further step.

If `schema.ts` changed as well, apply that first by the `drizzle-kit export` route in §6 — **not**
`drizzle-kit push`.

Without `--replace` the second command refuses a populated target and changes nothing. With it, the
delete, the insert, the `POST_INSERT_DDL` and every check run in one transaction, so a failed check leaves
the previous data exactly as it was.
